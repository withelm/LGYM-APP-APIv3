# LgymApi.Api.csproj

- Reporting submission responses preserve the legacy nested `request.status = Submitted` contract when Reporting stores the new internal `Completed` feedback-read state.
- Reporting submission responses add `canEditFeedback` and `canMarkFeedbackRead` advisory lifecycle capabilities; mutation endpoints still recheck authorization and concurrency.
- Purpose: ASP.NET Core HTTP entrypoint.
- Contains: controllers, DTO contracts, validators, middleware, mapping profiles, auth, JSON setup, Swagger, CORS, rate limits, SignalR, and composition root.
- Rules: keep controllers thin and preserve legacy payload shapes.
- Boundary: do not move application or infrastructure business logic here.
- Composition: `Program.cs` wires the exact seven-assembly mapping marker set, then the public facades in this order: Platform, Identity, Training Planning, Notifications, Reporting, remaining Application, Infrastructure, Reporting API adapters, `AddApplicationApiAdapters`, `AddNotificationsApiAdapters`, and Worker last. The Application and Notifications API-adapter facades register exactly 25 and 3 scoped contracts respectively. Host-only bindings stay in the API project.
- Authentication registration is API-owned in `Configuration/ApiAuthenticationExtensions.cs`; `Program.cs` delegates signing-key validation and JWT bearer setup to `AddApiAuthentication(...)` while retaining only host composition. API permission requirements remain HTTP adapters and delegate the global decision to Identity's actor bridge.
- Legacy app-version creation declares `ManageAppConfig` and retains own-account route binding. Its `LegacyForbiddenResponseAttribute` preserves the resource-backed `Forbidden` message when the policy rejects a request; other JWT forbidden responses retain their existing message.
- `UserContextMiddleware` validates `userId` and `sid` through the Identity marker-contract resolver and stores only `AuthenticatedAccountContext` in the request feature collection. API middleware and controllers do not materialize `User`, call Identity repositories, or publish a legacy `HttpContext.Items["User"]` handoff.
- `AddApiLocalization(...)` is the host-only localization helper: it registers localization and builds the English-default `en`/`pl` request options with `Accept-Language` as the sole culture provider; `Program.cs` keeps its middleware invocation first in the pipeline.
- The guarded request pipeline order is localization, authentication, conditional rate limiting outside Testing, `UserContextMiddleware`, authorization, Hangfire dashboard authorization, Reporting protocol negotiation, and API idempotency. The non-Testing Hangfire dashboard requires the middleware-validated account/session and Identity's current `AdminAccess` permission; its synchronous dashboard filter consumes only the request-scoped result and never trusts JWT role or permission claims directly. Reporting negotiation runs after authorization and before replay so protocol 1 and 2 never share replay/cache identity. A concurrent idempotency-claim unique-index loser detaches its failed staged record, loads the winner, and follows the normal in-progress/completed replay path without rerunning a mutation. Identity-classified completed replays resolve current account/session and declared route or permission preconditions before returning a stored private response; a denial never reruns the mutation. Authorization policies read the middleware-resolved immutable account context, not permission claims embedded in a previously issued JWT.
- `Program.cs` invokes `AddStrictHttpJsonOptions(...)`, `AddApiLocalization(...)`, `AddApiAuthentication(...)`, and `AddApiAuthorizationPolicies(...)` exactly once; their JSON, localization, JWT, and policy registrations do not appear inline in the composition root.
- API host helpers own HTTP serialization, request localization, JWT registration, authorization-policy registration, API idempotency, and logging bootstrap. Identity owns typed global permission policies and the validated account-to-actor mapping; persisted payload serialization remains a Technical Platform concern, not an API options bag.
- Exercise read and legacy write contracts stay without `eloFormula`; privileged exercise create/update endpoints use separate DTOs and `ManageGlobalExercises` policy.
- Ordinary actors can read global Exercises and their own custom Exercises, and can mutate only their own custom Exercises. Current `ManageGlobalExercises` permission permits unrestricted global-management decisions; foreign custom objects remain non-disclosing and route-account mismatches are rejected before a mutation.
- Enum-backed choice lists must return `LookupItem`-style payloads with stable enum-string `id`; `name` and `displayName` both carry translated display text.
- Exercise ELO formulas must be sourced from the enum lookup API (`/api/enums/enumType/ExerciseEloFormula`) and must not be hardcoded in the front-end.
- Lookup-backed request values such as `ExerciseExtendedFormDto.EloFormula` must be mapped in API mapping profiles from lookup ids to application enums; controllers should not parse them.
- Enum API adapters consume the Reference Data lookup contract. Lookup responses keep the raw enum member as `id`, translated text in both `name` and `displayName`, hidden-value filtering, and case-insensitive enum-type lookup.
- Push installation endpoints live under `/api/push/installations/*`, rely on the middleware-authenticated `AccountReference` plus `AccountSessionReference`, and never trust client-supplied account identity for device registration or disassociation.
- Push sender configuration follows the existing `appsettings.json` convention under `PushNotifications:*`; the API host composes Notifications-owned FCM and Worker scheduling through public facades but does not send push notifications synchronously inside controllers.
- Notifications composition is host-facing: API calls `NotificationsModule.AddNotificationsModule(configuration)` before remaining Application and Infrastructure, then calls the Notifications-owned `AddNotificationsApiAdapters()` facade after Infrastructure. The single SignalR `IInAppNotificationPushPublisher` remains a host adapter, while password and push scheduler adapters are supplied only by the final Worker facade.
- SignalR notification delivery uses the API-owned singleton `IAccountSessionConnectionRegistry`, keyed by validated account/session pairs. The hub registers only active pairs, removes them on disconnect, closes on authentication expiry, and the publisher re-resolves every pair before direct delivery, pruning revoked, expired, mismatched, blocked, or deleted entries. This registry is process-local and therefore requires sticky single-instance hosting until a separately designed distributed backplane is introduced.
- Before each SignalR send, the publisher also invokes Notifications' owner access port for the persisted notification and current source visibility, including delayed payloads in an already-used scope. Payload conversion uses the registered notification mapping profile; fresh source facts are not served from EF's tracked entity cache.
- Testing composition passes `isTesting: true`, which selects Worker no-op schedulers and suppresses Hangfire storage/server registration. Non-testing composition selects Worker Hangfire schedulers; server hosting still depends on the host option.
- The host delegates recurring persisted-job registration to the final Worker facade and does not reference Common directly. Recurring scheduling remains separate from the dashboard middleware so moving dashboard authorization behind the validated HTTP identity pipeline does not change persisted job IDs or schedules. The facade delegates enabled server hosting to Infrastructure's persistence helper.
- Startup migration keeps Testing factory behavior and applies pending migrations through the scoped `AppDbContext` in every non-Testing environment, including Staging and Production. Non-Testing startup then validates the configured runtime database/role before serving traffic.
- The API has no maintenance credential and never activates tutorial RLS. Staging activation and rollback are operator actions documented in [`tutorial-rls-pilot.md`](../docs/security/tutorial-rls-pilot.md); Production expects the disabled RLS configuration until separate approval.
- Elasticsearch logging is optional: a non-blank `Elasticsearch:Url` enables the existing asynchronous sink; missing or blank configuration leaves that sink unregistered while preserving Serilog provider registration and sensitive-data enrichment.
- The only API-level push bridge path is the admin-only test endpoint at `/api/internal/push/test-event`; it accepts privacy-safe IDs only and exists to prove generic enqueue wiring without auto-converting all in-app notifications to push.
- Rollout guardrails rely on `PushNotifications:SendEnabled` for send-only disablement plus the recurring `push-stale-installation-cleanup` Hangfire job for inactive-token tombstoning.
- `PlanController` preserves its legacy routes and DTO contracts by constructing typed Plan commands and queries and calling focused `TrainingPlanning/Plan/*` contracts directly; it does not depend on a broad Plan facade.
- `PlanDayController` preserves its legacy routes and payloads while calling Training Planning's marker-only `IPlanDayService`; `PlanDayProfile` maps immutable Planning read/write models without controller entity construction.
- `PublicInvitationController` preserves the anonymous `GET /api/invitations/{invitationId}` contract while calling only `IPublicInvitationStatusUseCase`; it retains controller-level blank-code and malformed-ID parsing, bare 404 responses, and profile-based `PublicInvitationStatusReadModel` mapping.
- Trainer relationship HTTP actions are split into `TrainerInvitationController`, `TrainerDashboardProgressController`, and `TrainerManagedPlansController`. Each retains the `api/trainer` route and trainer policy while injecting only its focused Coaching use cases plus `IMapper`; response transformations remain registered API mappings.
- Trainee relationship and trainer/trainee-note controllers use focused Coaching use cases plus API mapping profiles, preserving their existing `api/trainee` and `api/trainer` routes, malformed-ID branches, and legacy response DTO shapes.
- LGYM-218 adds `GET /api/trainee/notes/{noteId}/history`. It returns only currently visible, non-deleted trainee-owned notes and only history versions shared with the trainee; a private predecessor is redacted. `TraineeNoteDto` exposes the immutable original author identity rather than a current relationship owner.
- Coaching and Reporting HTTP controllers are adapters only: they inject owner-oriented API ports and `IMapper`, while ownership, authorization, commits, and persistence stay behind Application ports.
- Reporting adds the trainer-only, no-body `POST /api/trainer/trainees/{traineeId}/recurring-report-assignments/{id}/request-now` action without changing any existing Reporting route or payload. It delegates only to the recurring-assignment API port and, on success, returns `201 RecurringReportAssignmentDto` with the existing nested pending `currentReportRequest` shape.
- Anonymous `/dev/photos/upload/*` and `/dev/photos/read/*` routes remain Development-only bearer-capability endpoints. They reject malformed, expired, noncanonical, method/path-tampered, or wrongly signed URLs with 404 before decoding or storage access; uploads additionally enforce configured MIME and streamed-size policy.
- The request-now action preserves resource-backed `ResponseMessageDto` errors: malformed trainee or assignment IDs return `400`; trainer authorization returns `403`; missing, deleted, foreign, or no-longer-related assignments return `404`; and an unresolved request lifecycle, inactive/out-of-window cycle, or deleted template returns `409`. The API does not introduce a request body, DTO, response wrapper, or controller-owned lifecycle rule.
- Nutrition retains its four existing controller adapters: trainer Diet, trainee Diet, trainer Supplementation, and trainee Supplementation. Together they delegate the existing 18 actions only to focused D1-D9/S1-S9 contracts plus `IMapper`, preserving routes, verbs, policies, parsing branches, DTOs, JSON names, localized messages, and status contracts.
- Trainees can use `GET /api/trainee/diet-plans`, `GET /api/trainee/diet-plans/{dietPlanId}`, `GET /api/trainee/diet-plans/{dietPlanId}/history`, and `POST /api/trainee/diet-plans/{dietPlanId}/update` against their own Diet plans. The account-access response exposes Nutrition own-plan and trainer-management capability booleans.
- The only approved Diet behavior difference is an Application-layer localized 403 for a non-trainer with a nonempty trainee ID after action-specific prevalidation. Controllers do not implement that rule or manually construct cross-layer models.
- API composition follows the guarded public facade order: Platform, Identity, Training Planning, Notifications, Reporting, remaining Application, Infrastructure, owner API adapters, then Worker.
- Workout & Progress API handoff keeps Exercise and Main Records behind their owner-oriented API adapters because they construct owner input models; Gym, Measurements, Exercise Scores, Training, and ELO Registry controllers inject their existing owner service contracts directly. All seven controllers retain the existing mapping profiles and HTTP contracts.
- Exercise, completed-training, main-record, and trainer-progress reads return culture-negotiated `displayName` values. Controllers pass `HttpContext.GetCulturePreferences()` to the owning use case and map the returned `*WithTranslations` read model through the `ExerciseProfile.Keys.Translations` context; they do not load translations themselves. Every `ExerciseResponseDto` map is registered in a profile and resolves `displayName` through `ExerciseProfile.ResolveDisplayName`, so the legacy `name` stays the persisted exercise name, custom exercises are never translated, and reads without translations fall back to `name`. `IRequestCultureFeature` ordering takes precedence over raw `Accept-Language` tokens.
- API content links Notifications-owned email templates to `EmailTemplates/<Template>/<en|pl>.email` under the runtime base directory.
- Both API Docker surfaces publish the standalone Authorization kernel and copy its DLL into the runtime image without an API project-reference edge; the alternate authorization-build stage declares its own `BUILD_CONFIGURATION` argument.
- Training history-by-date endpoints accept exactly one request variant: legacy `{ "createdAt": "2026-10-22T12:00:00Z" }`, which retains UTC-day semantics, or local-day `{ "date": "2026-10-22", "timeZone": "Europe/Warsaw" }`. The latter requires an IANA identifier and a calendar day whose two local-midnight boundaries are unambiguous, existent, and convertible to a positive UTC range; mixed, incomplete, explicit-null, and unrepresentable variants return validation errors.
- Reporting endpoints negotiate `X-LGYM-Reporting-Protocol`: a missing header is protocol 1 and exact values `1` and `2` are supported after startup. There is no manual enable flag. After EF schema migration, `StartupMigrationBootstrap` awaits the automatic historical reporting migration before the host or hosted jobs start; failure aborts startup. Capability probes are authenticated at `/api/trainer/reporting/capabilities` and `/api/trainee/reporting/capabilities`; dictionary routes require protocol 2, and protocol-sensitive responses are private/no-store and vary by the protocol header.
- `POST /api/trainee/report-submissions/{submissionId}/mark-feedback-read` is an owner-only, idempotent completion action. Its response retains the submission contract and includes the next recurring request status/date when an active assignment supplies one; duplicate requests return the same derived scheduling result without emitting another notification.
- `POST /api/trainee/report-submissions/{submissionId}/answers` fully replaces answers before first feedback for the original active episode. The `answers` property is required; an empty object is allowed when the report's fields permit it. Clients must resend optional non-measurement answers they want to retain. Measurement fields must remain unchanged, including presence and null or invalid legacy values; ambiguous duplicate keys and malformed stored payloads are rejected. Submission responses expose advisory `canEditAnswers`.
- Recurring report schedules expose the same authoritative effective next occurrence, pending trainee proposal, and newest-first trainee proposal audit history to their active trainer and trainee. Resolved history includes requester/resolver identities and timestamps. Trainers use `POST /api/trainer/trainees/{traineeId}/recurring-report-assignments/{id}/next-report-override` and proposal accept/reject actions; trainees use `GET /api/trainee/recurring-report-assignments` and `POST /api/trainee/recurring-report-assignments/{id}/next-report-proposals`. Override and proposal timestamps require an explicit `Z` or numeric offset, and both writes require the current `expectedScheduleRevision`; stale revisions return conflict. Reporting normalizes accepted instants to UTC, and inactive, ended, deleted, foreign, former, or successor relationships fail closed.
- `GET /api/account/access` is the self-only, private/no-store authorization capability envelope. It maps current Identity policy decisions and explicitly reports every unintegrated owner extension as unavailable; it does not reuse Reporting protocol negotiation or accept a client-selected account.
