# LgymApi.Notifications.csproj

- Purpose: stable code boundary for provider-neutral notification capabilities.
- Contains: provider-neutral Notifications contracts, read models, errors, event bridge, installation lifecycle, in-app fanout, push enqueue/delivery/retry/cleanup, Coaching intent policy, and the email provider/template stack. Established non-Task7 `LgymApi.Application.Notifications.*` namespaces remain source-compatible, but their policy implementation compiles from this assembly.
- Rules: keep direct references limited to Authorization, BackgroundWorker.Common, Domain, Identity, Platform, and Resources. Its internal persistence seam and private provider configuration are friend-visible only to Infrastructure, UnitTests, Notifications.UnitTests, and IntegrationTests.
- Boundary: do not add a DbContext, migrations, publicly exposed provider credentials, or a reverse Identity dependency. `INotificationsPersistenceContext` exposes only its five owned sets and typed entries for in-app and push messages.
- Account lifecycle integration: Notifications registers the scoped `PushInstallationSessionDisassociationAdapter` for Identity's `IAccountSessionDisassociationPort` and `PushInstallationAccountCleanupAdapter` for `IAccountPushInstallationCleanupPort`. The adapters, lifecycle service, and repository contract forward only marker IDs; private persistence rebinds IDs, stages session disassociation or all account-linked installation deletion without committing, and leaves Identity's UoW boundary authoritative. Account cleanup stages dependent PushNotificationMessages before their installations, retaining the configured cascade as relational safety.
- EF coordination: `NotificationsModelConfigurationRegistrar` owns the five fixed-order mappings. Infrastructure retains the global phase coordinator, the single `AppDbContext`, migrations, and the scoped `INotificationsPersistenceContext` alias without assembly scanning.
- Composition: `NotificationsModule.AddNotificationsModule` is the policy and repository-registration facade; its configuration overload is the sole public email/provider registration path and validates/adds the private email stack plus FCM client, settings, retry mapping, and provider sender. `AddNotificationsApiAdapters` separately registers the three Notifications-owned API adapters after Infrastructure composition. Repositories use only `INotificationsPersistenceContext`, stage changes, and preserve the configured email send lease through Infrastructure's narrow `AddNotificationsInfrastructure()` settings bridge. API binds the SignalR publisher as the host adapter, and Worker remains last for scheduler and runtime selection.
- Report in-app notifications: `ReportSubmissionCreatedActionExecutionPort` (recipient trainer, actor trainee) and `ReportFeedbackAddedActionExecutionPort` (recipient trainee, actor trainer) share `ReportNotificationActionHelpers.ExecuteWithParticipantsAsync`. The helper parses both payload account IDs as `Id<AccountReference>` and rejects invalid values, resolves both accounts through Identity's `IAccountLookupService`, and formats the persisted message under the recipient's `PreferredLanguage` (only `en`/`pl`, otherwise `AppDefaultsOptions.PreferredLanguage`). It restores `CurrentUICulture` afterwards. Missing actor names and template names fall back to localized generic display names. Redirect URLs are client parsing contracts, not web routes: mobile extracts the submission ID from the trainee-facing `/trainer/report-submissions/{submissionId}` link for `ReportFeedbackReceived` and opens its trainee report details screen. Keep that shape unless Mobile changes with it; `ReportSubmissionReceived` keeps `/trainer/members/{traineeId}?tab=reports&submissionId={submissionId}`.
- Email templates: the twelve source files are under `EmailTemplates/<Template>/<en|pl>.email`; API and Integration projects link them to the unchanged `AppContext.BaseDirectory/EmailTemplates/<Template>/<en|pl>.email` runtime layout.
- Compatibility: preserve `DeliveryKey`, `(installation,type,eventId)`, cursor ordering, bounded retry/cancellation recovery, stale tombstoning, and Coaching's single eligible channel. Delivery rechecks disabled installations and performs a final no-tracking binding-and-revision projection before calling a provider; unavailable or rebound rows are suppressed without a provider call. The provider receives an immutable authorized installation target, so a concurrent logout/rebind cannot substitute another account's token. Invalid-token concurrency recovery resets only the failed installation mutation before its cancellation-independent message recovery save, preserving a concurrently rotated registration. Public contracts remain free of Worker/Common runtime types, provider credentials, and provider-private token handling; FCM credentials and tokens remain internal to Notifications.
- Retention defaults remain 30 days for message history, 30 days after `DisabledAt` for disabled installations and 90 days for in-app notifications, with batches of 500. Repositories select oldest-first candidates including soft-deleted rows and stage removal; services commit each batch. Pending/finalizing accounts are excluded before batching. Identity eligibility reads join the shared optimistic account revision fence so concurrent deletion cannot commit a stale retention selection. Account deletion retains installations/history during recovery and removes them at finalization; logout only disassociates the ended session. These rules do not control Firebase retention.
- `AccountRecoveryEmailOutbox` stages a mapped Notifications email record without saving or dispatching. Identity commits it together with the hashed recovery session; the normal email worker uses the localized account-recovery composer. See [account deletion](../docs/account-deletion.md).
- Final adapter disposition: `AddNotificationsApiAdapters` registers exactly three controller-facing owner contracts. `PushInstallationSessionDisassociationAdapter`, `CoachingEmailNotificationSchedulerAdapter`, and `PasswordRecoveryEmailSchedulerAdapter` remain as focused integration adapters. Their removal requires an approved replacement that preserves contracts, registrations, consumers, and durable behavior. Notifications services use direct constructor injection with no numeric arity cap; dependency aggregates and service location remain forbidden.
- Source privacy: Notifications parses its established delivery keys into opaque source references and owns the pure disclosure policy. Infrastructure supplies current source existence, deletion, lifecycle, visibility, participant, relationship, and account-availability facts without exposing foreign entities to Notifications. Creation suppresses live and queued delivery when the source is already invalid; SignalR, remote push, private lists, unread counts, and direct mark-read revalidate current eligibility. Report-request reminders require a pending request; submission and feedback notifications require a submitted request and matching request/submission trainee, while remaining valid after relationship unlink. Hidden/deleted notes, deleted diets, stale invitation states, restored relationships, deleted/blocked subjects, malformed or non-roundtrip version keys, and missing sources fail closed. Accepted report progress remains independent of notification disclosure and continues through its existing trusted outbox/receipt path.
- Report feedback-read notifications use `report-feedback-read:{submissionId}` and require the completed submission state plus the assignment's still-active matching source coaching episode. Existing submission and feedback notifications remain visible across the terminal `Submitted` to `Completed` transition so feedback completion cannot retroactively hide their source.
- Recurring reminder insertion rechecks source eligibility within a transaction and commits the notification with the active episode revision fence. SignalR and remote provider delivery separately lock the source then active episode, flush and reread eligibility, and hold that delivery transaction through the awaited send. It is disposed before bridge enqueue or retry recovery/scheduling. Ineligible remote reminders use the existing `SourceNotificationUnavailable` skipped outcome. A stale reminder is a successful no-op for its durable action; a concurrency conflict is retryable, and already-started external deliveries cannot be recalled.
- Ownership and replay: HTTP notification actors are created only through Identity's registered actor bridge. Registration may rotate an installation owned by the same account onto the request's currently validated session; unbound rows may be legitimately rebound after logout. Foreign accounts cannot take over an installation ID. A filtered database-unique FCM-token index closes concurrent cross-installation/account races, while the installation registration revision is an optimistic concurrency token that serializes claims, session rotation, unregister, disassociate, and other same-row updates. Notifications classifies conflicts through its provider-neutral contract; Infrastructure recognizes only the owned installation-ID and FCM-token PostgreSQL constraints. A losing mutation reloads the tracked existing installation or detaches the failed insert before returning generic forbidden, so keyed response persistence cannot retry the losing write. Unregister and disassociate continue to require the exact current account/session pair. Provider delivery re-resolves the installation account/session and permanently suppresses stale-session work. Optional keyed replay for register/unregister rechecks the exact installation binding, and mark-read replay rechecks current ownership and source eligibility; malformed/non-string replay bodies fail closed. Disassociate deliberately has no idempotency metadata because successful disassociation removes the ownership proof required to authorize a cached response, so a retry executes normally and fails the exact-pair check.
- Capabilities: the Notifications account-access extension publishes `canReadNotifications`, `canMarkNotificationsRead`, and `canManagePushInstallations` from the same current account/session precondition used by the protected API surface; availability alone is not an action grant.
