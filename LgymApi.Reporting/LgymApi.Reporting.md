# LgymApi.Reporting.csproj

- Purpose: Reporting use cases, focused persistence ports, API adapters, reporting mapping profiles, and owner-facing registration facade.
- Compatibility: source retains established `LgymApi.Application.Reporting.*` and `LgymApi.Application.Features.Reporting.*` namespaces so API, Worker, persisted command, and mapper contracts are unchanged.
- Dependencies: direct references are limited to Authorization, Domain, Identity, Platform, and Resources; Reporting must not reference Application, API, Infrastructure, Worker, Coaching, or Training Planning.
- Persistence: Infrastructure supplies Reporting's five stage-only adapters and owns the sole `AppDbContext`, database, schema, and migration stream.
- Composition: `AddReportingModule()` registers Reporting services and `AddReportingApiAdapters()` registers its API-facing adapters; the API host composes both through this facade.
- Testing: `LgymApi.Reporting.UnitTests` is the friend test assembly for Reporting-owned service, persistence, recurring-assignment, mapping, and photo tests.
- Relationship access: Reporting owns immutable active-state and bounded relationship-period facts. Infrastructure projects timestamps and start provenance from Coaching episode storage without exposing Coaching contracts. Generic `HadRelationshipAt` denies unknown starts. Current writes still require an active relationship; historical submission and source-photo reads use an explicit trainer-authored-source authorization path. Known periods use start-inclusive/end-exclusive semantics, while migration-observed unknown starts preserve only the matching source trainer's record readability rather than asserting an unbounded relationship. Successors and unrelated trainers cannot inherit another trainer's evidence. LGYM-153 cancellation behavior remains outside this seam.
- Authorization: Reporting registers its own typed policy through `LgymApi.Authorization`. Archive reads require immutable source trainer/request/trainee facts and submitted request state; cancelled, deleted, missing, and mismatched source records fail closed. Active requests and trainer-owned definitions remain active/source-owner-only. The Reporting K04 account-access extension exposes own submission read/submit and trainer template/photo-type actions, but every resource read and mutation re-evaluates this policy.
- Accepted report requests retain the active coaching episode marker. Submission acceptance requires that explicit marker to match the current active episode, stages it with the server acceptance instant in the Reporting outbox, and revision-checks the episode in the same commit so legacy-null provenance, unlink/relink, and concurrent unlink cannot fabricate a prior grant.
- Relationship-ended cancellation includes expired requests because they remain actionable. A concurrent status transition fails optimistic concurrency; the durable cancellation action must retry in a fresh unit of work.
- Pending request lists exclude missing or non-current episode provenance immediately, without waiting for cancellation. Listing and submission expiry writes require a matching active episode and stage its revision in the same save; an unlink conflict fails closed.
- Photo reads: signed reads, request/trainee history, and submission hydration bind each active photo to its authoritative non-deleted source request and trainee owner before metadata projection or original/thumbnail URL signing. Each disclosure re-reads the subject through Identity's marker-only account lookup and fails closed when it is missing or soft-deleted; this also blocks upload-init and completion before issuing a URL or inspecting storage. The trainee and explicitly matching source trainer may read records authorized by the source-aware episode rule while the subject is available; successors, unrelated trainers, privileged roles without source ownership, and unavailable subjects receive no photo entry or signed capability. Existing stored objects are retained; the cutoff does not revoke URLs issued earlier.
- Feedback mutations: both trainer feedback writes and first trainee feedback-read transitions lock the submission and current recurring assignment inside the Reporting unit-of-work transaction, require the submission, request, and assignment provenance to match the current active episode, and stage that episode revision before mutation. Revision conflicts roll back feedback and schedule changes and return the established non-disclosing failure. A first read records the immutable read instant, marks the request `Completed`, stages the trainer notification, and records the resulting next recurring eligibility; it requires `Submitted`, while cancelled, expired, or internally completed requests without a read marker are rejected. Assignment update, pause, resume, and delete writers lock and reload the assignment before their full-row write. Duplicate reads are idempotent and return the already-derived schedule without staging another notification. Legacy `Submitted` rows with an existing feedback-read instant remain recurring-eligible and readable; new mutation attempts with legacy-null provenance fail closed.
- Submission responses include advisory feedback edit and first-read capabilities, evaluated using the same lifecycle and episode facts as the mutations. Lists bulk-fetch active relationship and current-assignment facts after authorization; single responses retain their individual reads. Commands re-evaluate under their locks and revision fence; capabilities do not promise success after a concurrent state change.
- Answer edits lock the submission then assignment and fence the episode revision. They fully replace answers only before the first feedback, validate the issued snapshot and required photos, compare every measurement field's original presence and value before restoring the stored value, and never restage accepted progress. Unchanged invalid or null measurement values are retained; ambiguous case-insensitive keys and malformed stored answer objects fail closed. `canEditAnswers` is advisory and uses the same policy. Existing submissions have unknown first-feedback history and fail closed; new submissions record the first feedback permanently even if it is later cleared.
- First-feedback marker rollout is not mixed-writer safe: stop and drain all old API and worker writers before applying migration `20261112192912_AddReportFirstFeedbackMarker` and activating answer editing. Roll back only to a writer that preserves the marker; removing it would permit unsafe edits.
- Recurring scheduling records immutable Reporting-owned schedule-change audit rows. A trainer override is active for only the next unissued request and becomes consumed on issuance; later overrides supersede earlier active rows. A trainee proposal remains pending without changing eligibility until the active source trainer accepts it into the same override mechanism or rejects it. Assignment reads project all trainee proposals as newest-first audit history, including requester and resolver identities, while retaining the separate pending proposal projection. Schedule-change commands carry the caller's expected revision, and every assignment writer holds the assignment lock, increments its schedule revision, and invalidates pending proposals so they cannot carry across a changed schedule. Manual request-now and automatic processing stage the source-episode revision before handling a deleted template; a current-source assignment is deactivated, pending proposals are invalidated, active overrides are superseded, and the schedule revision advances atomically, while stale unlink/relink provenance leaves the lifecycle untouched. Assignments remain bound to their source coaching episode, so successors cannot mutate or issue the prior episode's schedule. Relationship-ended cancellation deactivates assignments and cancels actionable requests for the ended source episode; reminder delivery checks the source episode and schedule revision.
- Upcoming recurring reminders use the automatic issuance lifecycle at the scheduled instant, including the assignment end, deleted-template, and current photo snapshot checks under the trainer definition lock. Missing system photo defaults are simulated without persisting them; issuance revalidates later, so a reminder does not guarantee future issuance. A pending-request reminder remains independent of upcoming issuance.
