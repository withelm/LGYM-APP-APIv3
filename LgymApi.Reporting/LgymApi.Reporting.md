# LgymApi.Reporting.csproj

- Purpose: Reporting use cases, focused persistence ports, API adapters, reporting mapping profiles, and owner-facing registration facade.
- Compatibility: source retains established `LgymApi.Application.Reporting.*` and `LgymApi.Application.Features.Reporting.*` namespaces so API, Worker, persisted command, and mapper contracts are unchanged.
- Dependencies: direct references are limited to Domain, Identity, Platform, and Resources; Reporting must not reference Application, API, Infrastructure, Worker, Coaching, or Training Planning.
- Persistence: Infrastructure supplies Reporting's five stage-only adapters and owns the sole `AppDbContext`, database, schema, and migration stream.
- Composition: `AddReportingModule()` registers Reporting services and `AddReportingApiAdapters()` registers its API-facing adapters; the API host composes both through this facade.
- Testing: `LgymApi.Reporting.UnitTests` is the friend test assembly for Reporting-owned service, persistence, recurring-assignment, mapping, and photo tests.
- Relationship access: Reporting owns immutable active-state and bounded relationship-period facts. Infrastructure projects timestamps and start provenance from Coaching episode storage without exposing Coaching contracts. Generic `HadRelationshipAt` denies unknown starts. Current writes still require an active relationship; historical submission and source-photo reads use an explicit trainer-authored-source authorization path. Known periods use start-inclusive/end-exclusive semantics, while migration-observed unknown starts preserve only the matching source trainer's record readability rather than asserting an unbounded relationship. Successors and unrelated trainers cannot inherit another trainer's evidence. LGYM-153 cancellation behavior remains outside this seam.
- Accepted report requests retain the active coaching episode marker when available. Submission acceptance stages that marker and server acceptance instant with the Reporting outbox, and revision-checks the active episode in the same commit so unlink races cannot fabricate a prior grant.
- Photo reads: signed reads, request/trainee history, and submission hydration bind each active photo to its authoritative non-deleted source request and trainee owner before metadata projection or original/thumbnail URL signing. Each disclosure re-reads the subject through Identity's marker-only account lookup and fails closed when it is missing or soft-deleted; this also blocks upload-init and completion before issuing a URL or inspecting storage. The trainee and explicitly matching source trainer may read records authorized by the source-aware episode rule while the subject is available; successors, unrelated trainers, privileged roles without source ownership, and unavailable subjects receive no photo entry or signed capability. Existing stored objects are retained; the cutoff does not revoke URLs issued earlier.
